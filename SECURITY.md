# Security policy

Nightlock stores high-value secrets. Security reports must minimize exposure and preserve the reporter's ability to coordinate a fix privately.

## Supported versions

Nightlock does not yet have a stable supported release line. Security fixes target the active `main` branch unless an advisory states otherwise. See [SUPPORT.md](SUPPORT.md).

## Report a vulnerability privately

Use GitHub's private vulnerability-reporting flow:

<https://github.com/res138/nightlock/security/advisories/new>

If GitHub does not offer the private form, contact the repository owner through a private channel before disclosure. Do not create a public issue containing exploit details.

Include only what is necessary:

- affected commit, version, or artifact;
- impact and attacker prerequisites;
- minimal reproduction using synthetic data;
- affected platform;
- logs with secrets and personal paths removed;
- a proposed disclosure timeline, if relevant.

Never submit a real vault, master password, derived key, seed, signing key, or unredacted memory dump.

## Response targets

These are project targets, not contractual service-level agreements:

- acknowledge a credible report within three working days;
- establish severity and affected scope within seven working days;
- coordinate remediation and disclosure based on exploitability and user risk;
- publish an advisory when users need to take action.

## Security boundaries

The encrypted vault protects data at rest when the master password remains secret and the implementation assumptions hold. It does not fully protect secrets after they are displayed, copied to the clipboard, entered into Qt widgets, captured by the operating system, or exposed on a compromised host.

Current release packages are unsigned. Checksums generated by the same release workflow detect accidental corruption but are not independent proof of publisher identity.

Technical details are in [docs/security.md](docs/security.md), [docs/format.md](docs/format.md), and the evolving [documentation program](docs/DOCUMENTATION_PLAN.md).

## Safe research

- Use synthetic vaults and isolated machines.
- Do not access data that you do not own or have permission to test.
- Do not degrade project infrastructure or third-party services.
- Stop when testing could expose another person's data.
- Allow reasonable remediation time before public disclosure.
